# 破坏性重构

用户确认启用后，在当前 session 的任务范围内，以满足当前需求的目标结构完成重构。所有改造均只实现目标接口和数据格式，不实现或保留兼容旧接口、旧调用方或旧数据的逻辑。这是实施约束，不能仅理解为“允许破坏兼容性”后仍自行选择兼容方案。保持需要保留的产品行为；此技能不限定业务模块、技术栈、仓库结构或开发环境。

## 触发与启用确认

- 以用户在对话中的明确意图为触发依据，例如“进行破坏性重构”“可以不兼容旧接口”或“这次重构不需要兼容历史数据”。明确指示使用本技能进行重构也触发启用确认。讨论、创建或修改本技能，以及咨询重构方案，均不等于请求启用。
- 不从“优化”“简化”“重构”、开发环境或项目尚未上线等信息推断启用意图。加载本文件不代表技能已经生效。
- 首次启用前必须询问用户是否确认启动破坏性重构技能，并获得明确肯定答复。即使用户已经表达破坏性重构意图，也要完成这次启用确认；当前 session 已确认启用时不重复询问。
- 确认问题应说明当前 session 持续生效、不做接口与数据兼容的统一约束及下述默认授权。说明确认来自本技能的启用规则，链接当前 `SKILL.md` 并引用相应要求。例如：“是否确认在当前 session 启用破坏性重构技能？启用后所有改造统一不实现或保留旧接口、旧数据兼容逻辑，默认不保留历史数据，并可直接修改原版本及 migration，直到你要求停用。”
- 未回复、拒绝或含糊答复均不构成启用。等待期间可以继续只读分析和已有独立授权的工作，不执行依赖本技能新增授权的操作。

## 会话有效期、统一约束与授权

- 确认启用后，在当前 session（当前对话）持续生效。后续任务、话题切换或上下文压缩不自动停用，也不要求逐项、逐任务重新确认；保留启用状态和用户追加的限制。新 session 重新执行启用确认。
- 用户明确停用时停止沿用本技能授权；再次启用需要重新确认。只有用户明确提出的特定数据保留或接口兼容要求可以覆盖相应范围的规则，不必因此停用整个技能；不能自行推导兼容例外。
- 生效期间，当前任务范围内的所有改造统一遵守不做接口、数据兼容的约束，包括配套调整、后续修复及跨组件改造，不仅限于首次设计或某个功能。约束适用于对外接口、内部调用契约、持久化结构和序列化格式。
- 以下实施约束与破坏性操作授权同时生效，无需逐项请求许可：
  - 接口契约：直接修改或删除旧接口、字段及调用约定，同步更新实际调用方，不保留旧接口别名、兼容适配器或旧版本分支。新契约的必需方法、字段或参数不能为了旧调用方而设为可选、补默认值或静默回退。
  - 数据格式：直接调整持久化结构、序列化格式及相关模型，只按目标格式读写，不新增或保留历史格式读取、自动转换、兼容迁移、双写或旧版本降级逻辑。
  - 历史数据保留：允许不兼容、不保留历史数据，按重构需要直接删除或重建目标环境中的相关数据，无需为旧数据新增迁移、归档或恢复逻辑。
  - 版本策略：直接在现有 API、协议和数据格式定义中实施不兼容修改，允许改写已使用的 migration。禁止仅因契约不兼容而新增或提升协议代际，包括 API 路径、Provider API、schemaVersion、模块文件名及公开类型的 V1 → V2；不得保留并行版本、版本协商或升级过渡层。只有用户另行明确要求升级协议代际时才调整，不能从“破坏性重构”推导升级要求。用于标识新构建产物的发布版本或不可变 tag 不等于协议代际；发布仍受用户已有授权约束。
  - 旧数据与旧调用：不专门识别、拒绝或转换旧数据和旧调用，不增加旧版本门禁、迁移提示或历史格式拒绝测试。只实现新契约本身需要的校验；只关注新数据在新契约下正常使用，旧数据在新接口下是否正常不属于实施或验收目标。
- 上述授权限定在用户请求的任务、仓库和目标环境内，不因为会话持续生效而扩展为任意删除数据或修改无关系统。仅为实现重构目标执行必要的破坏性操作。
- 以是否为了维持旧接口或历史格式而保留特殊执行路径判断兼容逻辑，不以某条旧调用或旧数据恰好仍能工作判断。当前需求本身需要的可选能力、业务分支、校验和故障恢复按目标契约实现，无需为了让旧数据失败而做无关改动。
- 继续遵循与上述兼容例外无关的工作区、分支、检查和交付规范。提交、推送、合并、发布部署及修改其他环境，仍以用户已有的对应授权为准。
- 只有必要操作超出上述范围，或存在无法可靠推断的关键约束时才澄清；继续完成不依赖该答案的工作。

## 明确目标结构

先从需求和现有实现确认以下内容，复杂程度决定记录形式，不强制单独建立设计文档：

- 必须保留的产品行为和业务约束。
- 有意删除或改变的能力、契约及历史约束。
- 目标模型、职责边界、状态归属和对外接口。

以“不需要服务已获准放弃的旧调用方或旧数据时，最小而完整的实现是什么”评估设计。检查新结构是否满足当前实际需求，避免为假设中的扩展引入通用框架、重复状态或新的中间层。

合并重复流程时，将共同业务行为放在统一实现中，差异限制在确实需要差异的边界。检查旧来源或旧模式是否仍然让后续业务选择不同执行路径，避免只增加统一入口而保留多套实现。

## 梳理影响范围

沿真实调用和数据依赖检查入口、接口定义、业务逻辑、持久化、后台任务、客户端、配置、依赖组件、构建部署、测试和文档。按影响选择检查对象，不要求每次重构都涉及全部层次。

识别权威定义及其生成产物，从权威来源修改并按项目流程重新生成。跨仓库或跨组件时，明确调用方、提供方及需要一起交付的版本，防止遗漏仍依赖旧契约的实际消费者。

## 实现与清理

- 在当前改造范围内直接实现目标结构，删除被替代的执行路径、废弃字段、状态、参数、配置和依赖；已有兼容逻辑也必须清理，不能只约束新增代码。
- 同步简化保留的类型、函数、命名和控制流，使它们反映新职责。检查初始化、恢复、重试、异常处理和清理路径中是否仍然残留旧行为。
- 不以旧消费者仍在使用、历史数据可能存在、测试沿用旧契约、上线方便或改动较小为理由自行保留兼容层、过渡开关或降级通路。同步更新需要一起交付的消费者，不为未更新组件额外设计识别或拒绝逻辑。
- 更新相关文档、示例和生成产物。关键词搜索用于发现残留；完成标准是旧行为不再参与执行，不机械删除历史说明、负向测试或仍有用途的第三方内容。
- 保留无关修改。对附带问题判断其是否由本次修改引入、是否阻碍目标交付，再决定修复或单独记录，避免无限扩大范围。

## 数据与契约切换

技能生效后，直接切换到目标结构。改造范围内已有的兼容读取、转换或旧接口入口也应退出执行路径，不得仅以“没有新增兼容代码”视为满足要求。是否需要删除或重建数据由实际改动决定，不为使用授权而执行无关清理。

- 默认可以直接删除或重建目标环境中的相关历史数据，不要求归档，也无需重复请求历史数据处置授权。
- 用户明确要求保留某些数据或兼容特定消费者时，仅在该明确范围内执行必要转换、过渡和验证，记录对应用户指令，不把例外扩展为全局兼容层。没有这类明确指令时，不实现这些兼容路径。
- 默认可以改写已使用的 migration 或在原 API 版本中引入不兼容契约，无需再因既有版本兼容策略询问许可。
- 让初始化流程可以独立建立新结构，避免依赖旧环境中的手工状态。新契约应明确校验，不能通过静默回退掩盖组件不匹配。
- 跨组件交付应同步更新契约、生成代码、调用方与依赖锁定。按依赖顺序验证和交付，最终使用的产物必须与验证对象一致；未经验证的候选产物不能冒充正式依赖。

## 验证与失败处理

根据实际影响执行项目要求的检查，以新契约创建的新数据验证可观察的行为：新环境能够初始化，目标业务链路能够完成，需要保留的行为继续成立。不检查旧数据在新契约下是否正常，不为此添加成功或失败断言。只有用户明确要求转换保留存量数据时，才验证该转换路径。

删除被取消能力对应的测试，更新有意变化的契约断言，保留仍然有效的业务约束。需要新增回归测试时，优先覆盖实际风险和关键不变量，避免仅复述实现或检查字符串存在。

交付前沿实际调用和数据路径检查兼容残留，覆盖类型定义、运行时校验、异常分支、初始化、恢复、生成产物、测试及文档。检查是否引入未经用户明确要求的协议代际、并行版本、兼容通路或专门拒旧逻辑，发现后清理并复测。验收只证明新契约与目标业务行为正确，不要求旧接口或历史数据成功，也不要求其失败。

对失败分类并取证：

- 预期变化：依据已确定的新契约修改断言，不以让测试通过为理由反向调整需求。
- 本次引入的回归：修复原因并复测受影响行为。
- 已有问题：确认其与本次变更的关系及是否阻碍交付，必要时单独记录。
- 环境问题：验证诊断，修复或隔离原因后重跑，不把猜测作为结论。

不得通过跳过必要检查、放宽有效断言或增加无依据重试掩盖失败。必要检查通过后，仅在新增修改、失败或未解决风险需要时扩大或重复验证。

## 启用期间的协议代际门禁

这是交付前的源码门禁，不是运行时拒绝旧数据的门禁。技能启用的任务必须执行；未启用的普通开发不自动套用。

1. 为每个改动仓库记录此次开发的基准提交及所用维护分支。已有 PFB 使用任务原有开发基准；不能把已包含本次改动的 HEAD 当成新基准，也不能移动基准来消除失败。
2. 在提交、推送、发布或合入前，对每个仓库执行以下命令。提交前先把预期提交内容暂存；脚本同时检查暂存区、工作区和未跟踪源码，避免未暂存的修正掩盖暂存区中的协议升级。

   ```bash
   python3 <skill-root>/scripts/check_protocol_generations.py \
     --repo <repository-root> --base <recorded-base-commit>
   ```

3. 脚本比较常见协议版本字段、JSON Schema/YAML 枚举、版本化公开类型、API 路径和文件路径，输出含基准提交、当前 HEAD 和定位信息的 JSON。退出码 0 才是 PASS；1 表示发现代际升级，2 表示无法完成检查，两者都阻止提交、推送、发布和合入。修正后重跑，不能改断言、忽略失败或使用新版本基准绕过。
4. 脚本无法证明任意语言表达式的语义。必须同时核对本次受影响契约的权威定义及 diff，确认没有通过计算、间接常量或未覆盖命名引入代际升级，并在验收记录中列出这些定义、基准 SHA、门禁命令和结果。只有脚本 PASS 与契约核对都完成才可继续；后续改动后重新执行。
5. 门禁失败时直接修改现有契约，保留新功能，不引入兼容或专门拒旧逻辑。若用户另行明确要求协议升级，先明确该要求覆盖的契约范围，不将其推导为整个任务停用破坏性重构。

门禁自身的回归使用临时 Git 仓库，覆盖本次 Provider V1 → V2 失误、已提交的升级、未跟踪的并行协议文件以及暂存区与工作区不一致；同时确认在原契约中新增必需字段和更新软件发布 tag 可以通过。修改门禁后执行：

```bash
python3 -m unittest discover -s <skill-root>/scripts -p 'test_*.py'
```

## 完成与交付

按以下条件判断是否完成，不以修改文件数量或旧关键词清零作为完成依据：

- 目标结构已落地，共同业务行为有明确的实现与状态归属。
- 授权删除的旧执行路径已清理，相关消费者和配置已同步更新。
- 改造范围内不存在未经用户明确要求的接口、数据兼容通路；必需契约没有旧调用方回退，历史格式没有兼容读取或转换入口。
- 未擅自升级协议代际，也未增加专门识别或拒绝旧数据、旧调用的逻辑与验收要求。
- 协议代际源码门禁及契约权威定义核对均已通过，记录对应基准与结果。
- 数据处理符合授权，新环境初始化和受影响业务行为已经验证。
- 必要检查已通过，最终依赖及交付产物与验证对象一致。

交付说明应包含结果、不兼容影响、实际数据处理方式、兼容残留检查结果、验证证据及仍未完成的事项。若用户明确要求了兼容例外，说明其指令来源与适用范围。若检查或外部操作受阻，明确完成边界和阻塞原因，不将部分完成报告为全部完成。
